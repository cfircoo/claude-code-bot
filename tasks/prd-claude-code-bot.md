# PRD: Claude Code Bot Framework

## 1. Introduction

Claude Code Bot is a Python framework that lets developers define an AI-powered conversational bot via YAML configuration and deploy it on HTTP (FastAPI) and/or Telegram (aiogram) channels. The framework uses `claude-agent-sdk` as its sole LLM backbone, provides per-user conversation memory, and supports developer-defined sub-agents that the main persona agent can delegate to at runtime.

The problem: building the plumbing for a Claude-powered bot (channel adapters, memory, sub-agent orchestration, config validation) from scratch is tedious and error-prone. This framework eliminates that work so developers can focus on persona design and custom sub-agent logic.

## 2. Goals

- A developer can go from clone to running bot with a custom persona in under 15 minutes
- A basic persona bot requires zero lines of Python code (config-only)
- Adding a custom sub-agent requires fewer than 50 lines of code
- The bot supports 10 concurrent conversations on a single instance
- Response time p50 < 3 seconds, p99 < 15 seconds (dominated by LLM inference)

## 3. User Stories

### Phase 1a: Project Skeleton & Config

#### US-1: Load and validate bot configuration
**As a** bot developer, **I want** to define my bot's persona, channels, and settings in a YAML file **so that** I can configure behavior without writing Python code.

**Acceptance Criteria:**
- A YAML file at a configurable path (default `config.yaml`) is loaded at startup
- Pydantic models validate all fields: `persona` (name, system_prompt, tone, constraints), `channels` (list with type http|telegram and per-channel settings), `memory` (backend, path), `agents` (dict of sub-agent configs), `api_keys` (anthropic_api_key, telegram_bot_token)
- If the YAML is missing required fields, startup fails with a Pydantic validation error that names the missing/invalid field and its expected type
- If the YAML file does not exist, startup fails with a clear "Config file not found: <path>" error
- Environment variables override YAML values (e.g., `ANTHROPIC_API_KEY` overrides `api_keys.anthropic_api_key`)

#### US-2: Health check endpoint
**As a** bot developer, **I want** a `/health` endpoint **so that** I can verify the bot is running and integrate with uptime monitors.

**Acceptance Criteria:**
- `GET /health` returns HTTP 200 with JSON body `{"status": "ok"}`
- The endpoint requires no authentication
- FastAPI app starts on `http://localhost:8000` by default (port configurable via YAML or env var)
- Verify in browser using dev-browser skill

#### US-3: Structured startup logging
**As a** bot developer, **I want** structured JSON logs on startup **so that** I can confirm which channels and features are active.

**Acceptance Criteria:**
- On successful boot, a JSON log line is emitted containing: loaded config path, active channels, persona name
- Log output goes to stdout
- Log level is configurable via YAML or env var (default: INFO)

### Phase 1b: Main Agent & HTTP Chat

#### US-4: Chat via HTTP endpoint
**As an** HTTP end user, **I want** to send a message and receive a response **so that** I can converse with the bot.

**Acceptance Criteria:**
- `POST /chat` accepts JSON body `{"user_id": "string", "message": "string"}`
- Returns JSON `{"response": "string"}` with the bot's reply
- Response is generated by `claude-agent-sdk` using the persona's system_prompt from config
- If `message` is empty string, bot returns a persona-appropriate "I didn't catch that" response
- If `user_id` is not previously seen, a new conversation context is created automatically
- Verify in browser using dev-browser skill

#### US-5: Persona consistency
**As a** bot developer, **I want** the bot to respond consistently with the configured persona **so that** end users get the intended experience.

**Acceptance Criteria:**
- The `persona.system_prompt` from YAML is passed as the system prompt to `claude-agent-sdk` on every request
- The `persona.name` is available for use in responses (e.g., "I'm <name>")
- The `persona.constraints` list is appended to the system prompt as behavioral rules
- Changing the system_prompt in YAML and restarting the bot changes the bot's behavior on the next conversation

#### US-6: Optional HTTP API key authentication
**As a** bot developer, **I want** to optionally require an API key for the HTTP channel **so that** I can restrict access in non-local deployments.

**Acceptance Criteria:**
- If `channels[http].api_key` is set in config, requests to `/chat` without a matching `X-API-Key` header return HTTP 401 with `{"error": "Unauthorized"}`
- If `channels[http].api_key` is not set, `/chat` is open (no auth required)
- `/health` never requires authentication regardless of config

#### US-7: LLM error fallback
**As an** end user, **I want** to receive a friendly message when the LLM is unavailable **so that** I am not left with a cryptic error.

**Acceptance Criteria:**
- If the `claude-agent-sdk` call fails (timeout, 5xx, rate limit), the framework retries up to 3 times with exponential backoff
- After all retries fail, the bot returns a configurable fallback message (default: "I'm having trouble thinking right now. Try again in a moment.")
- The fallback message is configurable via `persona.fallback_message` in YAML
- Each failure is logged as a structured JSON error with the exception type and attempt number

### Phase 1c: Conversation Memory

#### US-8: Persist conversation history per user
**As an** end user, **I want** the bot to remember our previous conversation **so that** I don't have to repeat context.

**Acceptance Criteria:**
- Each `user_id` has a separate conversation history
- History includes all messages with role (user/assistant), content, and timestamp
- After the bot process is restarted, sending a follow-up message to the same `user_id` returns a response that demonstrates awareness of prior context
- Default storage backend is JSON files in a configurable directory (default: `data/`)
- The memory directory is created automatically if it does not exist

#### US-9: Graceful degradation on memory failure
**As an** end user, **I want** the bot to still respond even if memory storage fails **so that** a disk error does not break the conversation.

**Acceptance Criteria:**
- If writing to the memory store raises an I/O error, the bot still returns the LLM response to the user
- The memory failure is logged as a structured JSON warning
- On the next turn, if the memory file is unreadable, the bot starts a fresh conversation context (no crash)

#### US-10: Conversation history truncation
**As a** bot developer, **I want** long conversations to be truncated before sending to the LLM **so that** context window limits are not exceeded.

**Acceptance Criteria:**
- Before each LLM call, the conversation history is truncated to fit within a configurable max token budget (default: 80% of model context window)
- Truncation removes the oldest messages first, always preserving the system prompt and the most recent N messages
- A structured JSON log line is emitted when truncation occurs, stating how many messages were removed

---

### Phase 1d: Telegram Channel

#### US-11: Respond to Telegram DMs
**As a** Telegram end user, **I want** to message the bot and receive a reply **so that** I can chat with it on Telegram.

**Acceptance Criteria:**
- When `telegram` is listed in `channels` config with a valid `bot_token`, the bot connects to Telegram on startup
- The bot receives text DMs via aiogram and responds with the persona's reply
- The Telegram `chat.id` is used as the `user_id` for memory
- Default connection mode is long-polling (no webhook setup required)
- If the Telegram bot token is invalid, startup fails with a clear error: "Invalid Telegram bot token"

#### US-12: Telegram greeting for new users
**As a** Telegram end user, **I want** to receive an introduction when I first message the bot **so that** I know what it does.

**Acceptance Criteria:**
- On `/start` command, the bot sends a greeting message
- If `persona.greeting` is configured in YAML, that text is used; otherwise the bot generates an organic introduction via the LLM
- The greeting is sent only once per user (tracked via memory store)

#### US-13: Proactive messaging on Telegram
**As a** bot developer, **I want** the bot to send messages to users without a prior trigger **so that** it can deliver reminders, follow-ups, or notifications.

**Acceptance Criteria:**
- The framework exposes an internal API (`send_proactive_message(user_id, message)`) that sub-agents or scheduled tasks can call
- The message is delivered to the user's Telegram chat
- If the user has never interacted with the bot (no chat_id on record), the call raises a `UserNotReachableError` and logs a warning
- Proactive messages are persisted in the conversation memory as assistant messages

---

### Phase 1e: Sub-Agent Infrastructure

#### US-14: Register a sub-agent
**As a** bot developer, **I want** to register custom sub-agents with the framework **so that** the main agent can delegate specialized tasks.

**Acceptance Criteria:**
- A sub-agent is a Python class implementing a `BaseSubAgent` interface with: `name: str`, `description: str`, and `async def handle(self, context: dict) -> str`
- Sub-agents are registered either via YAML config (pointing to a Python import path) or programmatically via `registry.register(agent_instance)`
- On startup, all configured sub-agents are loaded and registered; import failures produce a clear error naming the failing agent
- The sub-agent registry is queryable: `registry.list()` returns all registered agent names and descriptions

#### US-15: Main agent delegates to sub-agent
**As an** end user, **I want** the bot to use specialized capabilities when needed **so that** I get accurate, task-specific results.

**Acceptance Criteria:**
- The main agent's system prompt includes a description of each registered sub-agent and instructions on when to use them
- The main agent can invoke a sub-agent via `claude-agent-sdk` tool use (each sub-agent is exposed as a tool)
- The sub-agent's `handle()` method receives a context dict containing: `user_id`, `channel`, `query` (the delegation request), and `conversation_summary`
- The sub-agent's string result is returned to the main agent, which incorporates it into the final response
- If a sub-agent raises an exception or times out (configurable, default 30s), the main agent receives an error message and responds gracefully without crashing

#### US-16: Sub-agent triggers proactive message
**As a** bot developer, **I want** a sub-agent to be able to trigger a proactive message **so that** background tasks can notify users of results.

**Acceptance Criteria:**
- The sub-agent `handle()` context includes a `send_proactive` callback function
- Calling `send_proactive(user_id, message)` from within a sub-agent delivers the message via the Telegram channel (per US-13)
- If Telegram is not configured, the call is a no-op and logs a warning

---

### Phase 1f: Docker Deployment

#### US-17: Docker build and run
**As a** bot developer, **I want** to build and run the bot via Docker **so that** deployment is reproducible and requires no local Python setup.

**Acceptance Criteria:**
- `docker build -t claude-code-bot .` succeeds and produces a working image
- The Dockerfile uses Python 3.11+ base image, installs dependencies from `pyproject.toml` or `requirements.txt`
- The image runs the bot with `python -m claude_code_bot` as the default command
- Config file is mountable via volume (default path: `/app/config.yaml`)

#### US-18: Docker Compose single-command startup
**As a** bot developer, **I want** `docker compose up` to start the bot with all configuration **so that** I can deploy with one command.

**Acceptance Criteria:**
- A `docker-compose.yml` file is provided at the project root
- It defines a single service `bot` that builds from the local Dockerfile
- Environment variables for secrets (`ANTHROPIC_API_KEY`, `TELEGRAM_BOT_TOKEN`) are read from a `.env` file
- The config YAML and data directory are mounted as volumes for persistence
- `docker compose up` starts the bot; `docker compose down` stops it cleanly
- A `.env.example` file is provided documenting all required and optional environment variables

## 4. Functional Requirements

- **FR-1**: The system shall load bot configuration from a YAML file and validate it against Pydantic models at startup, failing with descriptive errors on invalid input
- **FR-2**: The system shall expose a FastAPI HTTP server with `GET /health` and `POST /chat` endpoints
- **FR-3**: The system shall use `claude-agent-sdk` as the sole LLM backend for all agent inference
- **FR-4**: The system shall maintain per-user conversation history in a configurable persistent store (default: JSON files)
- **FR-5**: The system shall support Telegram as a messaging channel via aiogram, using long-polling by default
- **FR-6**: The system shall provide a sub-agent registry where developers register custom agents that the main persona agent can invoke as tools
- **FR-7**: The system shall retry failed LLM calls up to 3 times with exponential backoff before returning a configurable fallback message
- **FR-8**: The system shall truncate conversation history to fit within the model's context window, removing oldest messages first
- **FR-9**: The system shall support proactive (bot-initiated) messaging on Telegram, callable from sub-agents or scheduled tasks
- **FR-10**: The system shall allow environment variables to override any YAML configuration value
- **FR-11**: The system shall emit structured JSON logs to stdout for all significant events (startup, errors, memory failures, truncation)
- **FR-12**: The system shall optionally require an API key (`X-API-Key` header) for the HTTP `/chat` endpoint when configured
- **FR-13**: The system shall be deployable via Docker and Docker Compose with a single command

## 5. Non-Goals

- Group chat / multi-user shared conversations (deferred to v2)
- Multi-person memory per bot instance (v1 is 1 person = 1 user_id)
- A built-in library of pre-made sub-agents
- GUI or admin dashboard
- Voice or media message handling
- Support for LLMs other than Claude (claude-agent-sdk only)
- Plugin marketplace or discovery mechanism
- Horizontal scaling or distributed deployment
- Automatic conversation history expiry or retention policies
- Webhook mode for Telegram (long-polling only in MVP)

## 6. Design Considerations

There is no graphical UI in the MVP. The user-facing interfaces are:

- **HTTP channel**: JSON request/response API. Developers integrate into their own frontend if desired. FastAPI auto-generates OpenAPI docs at `/docs`.
- **Telegram channel**: Standard Telegram DM experience. Bot responds to text messages.
- **Empty state**: First message from a new user triggers either a configurable greeting or an organic LLM-generated introduction.
- **Error state**: LLM failures surface as a configurable fallback message. Sub-agent failures are communicated naturally by the persona.

## 7. Technical Considerations

| Concern | Detail |
|---------|--------|
| **Language** | Python 3.11+ (async support required) |
| **LLM SDK** | `claude-agent-sdk` -- pin version, wrap behind thin abstraction to mitigate API changes |
| **HTTP** | FastAPI with uvicorn; async request handling |
| **Telegram** | aiogram 3.x; long-polling mode; async |
| **Config** | YAML parsed with PyYAML, validated with Pydantic v2 |
| **Memory (default)** | JSON files in `data/` directory, one file per user_id |
| **Memory (optional)** | Mem0 integration deferred but architecture should allow swapping backends via a `MemoryBackend` interface |
| **Structured logging** | `structlog` or stdlib `logging` with JSON formatter |
| **Deployment** | Docker with Python 3.11+ slim base image |
| **Testing** | pytest, httpx TestClient for API tests, mocked claude-agent-sdk calls |
| **Type checking** | mypy strict mode |
| **Linting** | ruff |
| **Context limits** | Implement token counting (tiktoken or SDK-provided) for truncation |

**Key dependency risk**: `claude-agent-sdk` API may change. Mitigate by pinning version and wrapping SDK calls in an internal abstraction layer.

## 8. Success Metrics

- Time from `git clone` to running bot with custom persona: under 15 minutes
- Lines of Python code required for a config-only persona bot: 0
- Lines of code to add a custom sub-agent: fewer than 50
- `pytest` passes with 80%+ coverage on core logic
- `mypy` and `ruff` produce zero errors
- Bot responds to HTTP `/chat` requests with p50 latency under 3 seconds
- Conversation memory survives process restart (verified by integration test)
- A registered sub-agent can be triggered by the main agent during conversation (verified by integration test)

## 9. Open Questions

- [ ] What is the exact `claude-agent-sdk` API for registering tools (sub-agents)? Need to investigate SDK docs to confirm the tool-use pattern.
- [ ] What token counting method should be used for conversation truncation? Options: tiktoken, SDK-provided token counter, or character-based approximation.
- [ ] Should proactive messaging support scheduled cron-like triggers in MVP, or only programmatic triggers from sub-agents?
- [ ] What is the maximum conversation history size (in messages or tokens) before truncation? Needs benchmarking against model context window.
- [ ] Should the framework provide a CLI command (e.g., `claude-code-bot init`) to scaffold a new config file, or is a documented example config sufficient for MVP?
